# ReviewProof 设计决策与问题复盘

日期：2026-10-29。第 1–5 阶段和第 7 阶段已完成；第 6 阶段做了一个不训练的检查，决定不训练可答性模型（第 10 节）。

系统和评测结果的完整说明见[技术报告](technical_report_cn.md)；本文汇总两类内容，供面试时讲解：一是每个模块为什么这样设计，二是从立项到现在遇到的所有问题，以及为什么这样改。来源是各阶段的实施计划、整体审查台账、git 提交记录和真实运行记录。想先看每个模块的设计站不站得住，直接看文末的[模块设计体检表](#附模块设计体检表)。

第 7 节的数字是**银标试跑**，不是结论；金标评测的结果在 9.4 节。面试时以金标数字为准，并照第 9 节的口径说明金标的局限。

## 0. 一分钟讲清楚这个项目

**一句话：** 用户选定一件商品后提问，系统只依据这件商品的买家评论回答：能答时逐条带引用作答；只有部分证据时说明哪部分能确认；评论没提到时明确说"评论无法确认"，不编造。

**核心卖点是可答性（answered / partial / unanswerable）**，不是"又一个 RAG"。Amazon 已经有 Rufus 和评论摘要，这个项目的价值在于：有证据才回答、该拒答时拒答、每一步都能评测。

**整体链路：**

```
离线：AmazonQA 完整评论 → 抽样 100 件商品 → 句级切分 → BGE-M3 向量 → Postgres + pgvector

在线：问题 → 规划（范围判断、是非题判断、中译英检索词）
        → 检索：评论少的商品全量放进上下文；评论多的商品 稠密 ∥ BM25 → RRF → 重排 → 8 条证据
        → 证据评估（三态）→ 证据不足时改写重检索（最多 1 次）
        → 带引用生成（结构化 JSON）→ 纯代码核验引用 → 固定文案渲染
        → SSE 推送进度和答案；运行记录写库

评测：银标自动评测（5a）→ 子 agent 预标 + 人工逐题审核的金标（5b）→ 重排分数检查（第 6 阶段，决定不训练可答性模型）
```

**技术栈：** Python、FastAPI（SSE）、LangGraph、PostgreSQL 16 + pgvector、BGE-M3、bge-reranker-v2-m3、rank_bm25、Claude Haiku 5.5（Anthropic 官方 SDK，结构化输出）、Vue 3 + Vite + TypeScript、MCP、GitHub Actions。

**规模：** 100 件商品、22,433 条评论、24,599 个评论块、767 道评测题；Python 测试 321 个，前端测试 53 个。

## 1. 起点：为什么推倒重来

项目前身是课程项目 BRIDGE（Supabase + Gemini 检索、小样本演示）。接手时做过一次体检，发现它撑不起简历上的描述：

| 旧系统的问题 | 后果 | 新系统怎么做 |
|---|---|---|
| 检索结果只返回文本，评论 ID 在检索时就丢了 | 主链路做不了逐条引用 | 证据单位是 `chunk_id`，一路带到引用核验和前端高亮 |
| 向量 RPC 和 BM25 只能按 `file_id` 过滤 | 做不了"按商品问答" | 所有检索都在单件商品内进行 |
| 检索某一路失败时只打日志、返回空 | 工作流分不清"后端挂了"和"评论里确实没有" | 每一路都记录状态，`service_status` 和答案状态分开 |
| BM25 每次请求从 Supabase 拉 5,000 行现建索引 | 慢，规模一大就扛不住 | 按商品建索引并缓存在内存 |
| LangGraph 默认关闭，三套并行实现：整图 → 手写工作流 → 直连推理 | 演示时走的不是简历上写的链路，维护三套逻辑 | LangGraph 是唯一主链路，在节点内部降级 |
| 8 道题的小样本上各方案 Hit@5 全是 1.0 | 证明不了任何"提升" | 固定抽样清单、银标 + 金标评测、置信区间 |
| 评论数据是另一份 2023 版数据，和 AmazonQA 的问题对不上 | 没有可答性标签可用 | 改用 AmazonQA 自带的完整评论文件 |

**决定：** 新建独立仓库 ReviewProof，新代码全部放在 `reviewproof/` 包里；旧仓库只作参考，不复制代码。理由是旧代码的数据格式、切分方式、存储都要换，"先重命名再逐步改"的成本比重写还高。

## 2. 定位与数据：动手前的三个关键发现

### 2.1 为什么选"购前单商品问答"

当时比较了四种定位：购前单商品问答、商家自动回复、多商品对比、评论洞察。选第一种，原因是：

- AmazonQA 的结构天然按"商品 → 问题"组织，每道题都带 `asin`；
- 它有 `is_answerable` 标签，正好能量化"该不该拒答"，这是唯一能直接评测核心卖点的标签；
- 多商品对比没有对应标注，评测不了；评论洞察是另一类任务。

不做的事写进了 `docs/product_positioning_cn.md`：价格、库存、物流、促销等评论回答不了的问题直接路由出去；不做多轮对话；不训练生成模型。

### 2.2 发现一：AmazonQA 的"评论"其实是 BM25 片段

每道题只附带约 10 条 `review_snippets`，而且它们就是 AmazonQA 自己用 BM25 检索出的前 10 条。如果语料只用这些片段：

- 一件商品的全部片段在 P90 也只有约 6,000 token，直接塞进上下文就行，检索没有意义；
- 拿片段当参考证据比较 BM25 和向量检索，会天然偏向 BM25。

**解决：** 核实 `val-qar_products.jsonl`（732 MB）确实包含完整评论：15,606 条商品记录、140 万条评论，每件商品评论数中位数 31、P90 203、最多 8,966。文件里的 92,373 条问题全部能按 ASIN 加问题文本对上 `val-qar.jsonl`，由此拿到 `qid` 和标签；随机抽 1,500 件商品，97.3% 的片段能在完整评论里原文找到。于是语料改用完整评论。

### 2.3 发现二：`is_answerable` 是分类器给的银标

这个标签由 AmazonQA 的分类器给出（论文里 F1 约 0.74），而且判断时只看了那 10 条片段。我们的系统看的是全部评论，银标说"不可答"往往只是片段里没有答案。

**解决：** 定位文档里规定，最终结论必须建立在约 200 题的人工金标上；银标只用来看趋势、做回归检查（原计划还要用它训练第 6 阶段的可答性模型，后来决定不训练，见第 10 节）。这直接催生了 5a（银标）和 5b（金标）两个阶段。

### 2.4 发现三：大多数商品根本不需要检索

一半商品的全部评论不到约 3,000 token，评论超过 200 条的商品（约前 10%）才在 2 万 token 以上。

**解决：**
- 抽样按评论数分层：4 个品类 × 25 件，每个品类 10 件 ≥200 条、10 件 50–199 条、5 件 <50 条。某个品类评论多的商品不够时，从中间档补，并记录在清单里。
- 设计了**按规模自适应的检索策略**：评论少的商品全部放进上下文，评论多的才走混合检索。
- 始终保留"全部评论放进上下文"（B1）作为对照基线。

这样回答了面试里最常见的质疑："为什么不直接把评论全塞进上下文？"答案是：小商品确实就这么做；大商品塞进去又贵又慢，引用还会变得含糊，见第 6 节的成本数字。

## 3. 第 1 阶段：数据底座

### 3.1 设计和理由

| 设计 | 理由 |
|---|---|
| 抽样清单 `samples/manifest_v1.json` 记录源文件的 SHA-256；导入时校验不一致就以退出码 2 拒绝运行 | 结果可复现；换了数据文件不能悄悄混进来 |
| 系统生成评论 ID：`{asin}-r{index:05d}` | 原始数据没有评论 ID、评分和时间。文档里写明这是系统 ID，不能说成 Amazon 评论 ID |
| 评论 ID 和数据文件版本绑定，所以标注和 qrels 都要记录 `dataset_id` | 换一版数据，序号对应的评论可能就变了 |
| 同一 ASIN 出现多条记录时合并；跳过空评论；`normalize_text`（HTML 反转义 + 空白合并）是唯一的规范化函数 | 存储和去重只用一套规则 |
| 切分：评论 ≤1,200 字符整条保留，更长的按句打包到约 800 字符，相邻块重叠一句；`chunk.text == review.text[start:end]` | 评论中位数 238 字符，大多不用切；块要能放进重排模型 512 token 的输入；偏移量用于前端高亮和片段对齐 |
| 问题、社区回答、片段、可答性标签只存在 `questions` 表，绝不进入 `reviews`、`chunks` 或任何提示词 | 防止评测泄漏：系统要是"看到了答案"，评测就没有意义。有专门的测试检查 |
| 写库用 upsert；块的文本不变时保留向量，否则清空重算；向量化按批提交，中断后能接着跑 | 重复导入不产生重复数据，也不重复花算力 |
| BGE-M3（1024 维）在本地运行 | 免费、可复现、多语言（中文问题能检索英文评论）；评测要反复跑大量查询，不受 API 限流影响 |
| PostgreSQL + pgvector，用 psycopg 直接写 SQL | 需要按商品过滤、事务和关联查询，SQL 比 REST/RPC 简单 |

### 3.2 遇到的问题

**问题 1.1：Mac GPU（MPS）向量化跑到一半显存耗尽**
- **现象：** 用 MPS 跑 BGE-M3，每次跑到第 80～110 批就内存溢出，前两次全量运行都中断了。
- **第一次修复失败：** 每批之后清 GPU 缓存（`empty_cache`）。审查代理认为这个修复"标准且对症"，但实测第二次运行照样溢出。
- **根因：** MPS 会为每种输入尺寸缓存一份编译好的计算图，而且不释放。每批评论长短不同，输入尺寸一直在变，缓存只增不减。
- **最终修复：** 有 NVIDIA 显卡用 CUDA，否则用 CPU；新增 `REVIEWPROOF_EMBEDDING_DEVICE` 可以手动指定设备。
- **为什么这么改：** 实测 CPU 每秒约 11.5 个块，和 MPS 一样快，内存还不会增长。与其为 MPS 做分桶、固定长度等复杂补救，不如换一个更快也更稳的设备。剩下 18,551 个块用 CPU 约 51 分钟跑完。
- **可以讲的点：** 我推翻了审查代理的结论，依据是实测数据而不是"看起来对"。

**问题 1.2：断句正则丢掉评论开头的标点**
- **现象：** 计划里的正则 `[^.!?]+(?:[.!?]+|$)` 遇到以 "..." 开头的评论时，第一个片段从偏移 3 开始，切出来的块不能完整覆盖原评论。
- **修复：** 改为 `[^.!?]*[.!?]+|[^.!?]+`。
- **为什么：** "切块能完整覆盖原文"是引用高亮和片段对齐的前提，必须由测试保证（`test_leading_punctuation_is_covered`，在旧正则下会失败）。

**问题 1.3：重叠规则产生"只有一句重复内容"的块**
- **现象：** 原规则会切出 `s1 s2 | s2 | s3` 这样的块，中间那块只是上一块最后一句的重复。
- **修复：** 只有当重叠句加上下一句不超过目标长度时才重叠。
- **为什么：** 纯重复的块对检索没有信息量，还会在候选里占一个位置。

**问题 1.4：重新导入后评论数和商品表对不上**
- **现象：** 计划只删除过期的块。一件商品重新导入后评论变少时，`reviews` 里还留着旧评论，和 `products.review_count` 不一致。
- **修复：** 重新导入时，过期的评论和题目也一起删除。

**问题 1.5：向量维度不匹配要到写库时才报错**
- **修复：** 向量化前先检查模型维度和表结构里的 1024 是否一致，不一致直接拒绝，一个也不写。
- **为什么：** 尽早失败，错误信息说得清是哪里错了。

**问题 1.6（审查发现，提为重要）：测试可能清空正式库**
- **现象：** 数据库测试会清空所有表。如果有人把环境变量指到正式库，几十分钟算出的向量就没了。
- **修复：** `DatabaseTestCase` 拒绝名字不以 `_test` 结尾的数据库。
- **为什么：** 一个字母打错的代价是重跑 50 分钟的向量化，防线要放在代码里，不能靠人记得。

**其他：**
- 向量化没有进度输出（已加，进度写 stderr，最终 JSON 报告写 stdout，便于脚本解析）。
- 导入命令拆成 `cli.py` 和 `__main__.py`：`.env` 只在入口加载，测试导入命令逻辑时不会读到本机的 key。
- Docker Compose 加了 `name: reviewproof`，否则容器和数据卷沿用旧文件夹的名字。

## 4. 第 2 阶段：混合检索

### 4.1 设计和理由

| 设计 | 理由 |
|---|---|
| 自适应策略：商品评论总量 ≤6,000 token 时全量返回（100 件里有 28 件），否则走混合检索 | 小商品检索没有意义；阈值本来计划在 dev 上调 |
| 稠密：pgvector 在单件商品内精确排序，不建 ANN 索引 | 单件商品最多约 9,000 条评论，精确排序足够快；先按商品过滤再用 ANN，召回会损失 |
| 稀疏：`rank_bm25`，按商品建索引并缓存在内存，缓存键是块数和总文本长度 | 按商品过滤后规模很小，不需要 OpenSearch；但必须是真正的 BM25 |
| 两路各取前 50 → RRF（k=60）→ 前 40 进候选池 → `bge-reranker-v2-m3` 重排 → 取 8 条 | RRF 只看名次，不受两路分数量纲不同的影响，不用调权重；重排模型支持多语言 |
| 每一路的故障都被接住，记录状态、原因、耗时和命中数 | 一路挂了另一路照常工作，降级要看得见 |
| `service_status`：召回通道失败，并且没有一路成功或融合后为空时记为 `failed`；有通道失败但有候选时记为 `degraded` | 核心原则：**服务故障绝不能被读成"评论里没有答案"** |
| 中文问题提不出英文词时，BM25 返回 0 条，算成功而不是故障 | "零命中"和"出错"是两回事 |

**为什么要混合检索（面试必问）：** 问题不在数据规模，而在三件事：
1. 用户的问法和评论的写法对不上（"Is it noisy?" 对 "way too loud"），这要靠向量检索；
2. 型号、数字、否定词要精确命中（"4th generation"、"doesn't fit"），向量检索容易把它们混为一谈，这要靠 BM25；
3. 大商品的评论全塞进上下文，又贵又慢，引用也会变得含糊。

### 4.2 遇到的问题

**问题 2.1（整体审查中唯一的重要问题）：降级但为空，可能被读成"没有证据"**
- **现象：** 稠密检索挂了，BM25 正常运行但零命中，结果标成 `degraded` 并返回空候选。下游可能据此判"评论无法确认"。
- **修复：** 只要有召回通道失败，并且融合后的候选池为空，就一律标为 `failed`，`mode` 记为 `none`（`f1b7015`）。
- **为什么：** 一路故障时出现的空结果，不能说明评论里没有答案，只能当作服务故障。这条规则后来贯穿工作流、接口、前端徽标和评测分母。

**问题 2.2：计划里的测试没有测到它声称要测的东西**
- **现象：** 计划里的"稠密检索的 SQL 出错不影响 BM25"这个测试，实际触发的是 Python 异常 `IncompleteEmbeddingsError`，读库本身是成功的，Postgres 事务根本没有进入出错状态。
- **为什么这很重要：** Postgres 里一条 SQL 出错后，同一事务里的后续语句都会失败。如果稠密检索出错后不回滚，同一连接上的 BM25 也会跟着失败，"单路故障不影响另一路"就成了空话。
- **修复：** 加了一个让 Postgres 真报错的测试（用 8 维的查询向量触发 pgvector 的维度错误），确认 BM25 照常返回结果；各通道读完都会 `rollback()`，结束读事务。

**问题 2.3：导入校验用错了模型名**
- **现象：** 按计划，导入后的校验用配置里写的模型名。改成注入自定义模型时，导入的数据通不过自己的校验，有 3 个已有测试失败。
- **修复：** 校验和检索都用实际运行的向量模型的名字（`embedder.model_name`）。

**问题 2.4：测试把测试库的向量列改成了 8 维**
- **现象：** 写"数据库向量维度检查"的测试时，第一版的清理代码在连接关闭之后才执行，测试库的向量列被留成了 8 维。
- **修复：** 手动改回 1024 维，并修好清理顺序。正式库因为有问题 1.6 的防护，没有受影响。

**问题 2.5：CI 两次失败，测试一个都没跑到**
- **现象：** 一次 `Disk quota exceeded`，一次 248 MB 的文件下载 6 次都不完整。
- **根因：** `sentence-transformers` 依赖 PyTorch，Linux 上 pip 默认装 CUDA 版，连同 CUDA 库一共好几个 GB。第 1 阶段审查时这条被记成了次要问题。
- **修复：** CI 里先装 CPU 版 torch，再装其他依赖（`e27c930`）。测试本来就不加载真实模型。
- **教训：** 被评为"次要"的问题，在另一个环境里可能直接致命。

### 4.3 真实数据验证

- 大商品（2,228 个块），问 "adjustible volume control?"：两路检索都正常，8 条证据都属于这件商品；重排后排第一的评论，在两路里分别排第 2 和第 6，说明融合和重排都起了作用。
- 同一件商品用中文问"音量可以调节吗？"：BM25 正确地记为跳过，向量检索单独也找到了讲音量控制的评论。
- **成本观察：** 在 CPU 上，重排模型加载约 6 秒，加载后给 40 条候选打分约 5 秒，是延迟的主要来源。

## 5. 第 3 阶段：LangGraph 问答工作流

### 5.1 设计和理由

节点顺序：plan → retrieve → assess →（rewrite → 重新 assess）→ generate → verify → finalize。

| 设计 | 理由 |
|---|---|
| **LangGraph 是唯一的编排路径**，没有手写的备用流程 | 旧系统有三套并行实现，演示和代码对不上。降级放在节点内部 |
| plan：一次 LLM 调用，判断是否在服务范围、是不是是非题，并生成英文检索词（中文问题在这里翻译） | BM25 只认英文词；超出范围的题省掉后面所有调用 |
| assess：LLM 给出三态、支持证据的 ID、缺失的部分和改写查询 | **证据评估是可答性的唯一裁决者**；第 6 阶段检查过用重排分数代替它，不如它（第 10 节） |
| 改写重检索最多 `REVIEWPROOF_MAX_REWRITES` 次（默认 1），只用于混合检索的商品；查询重复或没有新证据就停 | 有预算的循环，不会死循环；全量上下文的商品已经拿到所有评论，改写没有意义 |
| generate：结构化输出，每条结论带 `chunk_ids`；评估为不可答时跳过这一步，省一次调用 | 结构化输出才能逐条核验引用 |
| verify 是纯代码：删掉不在本次候选里、或属于别的商品的引用；没有引用的结论整条删除；结论删光后降为不可答 | **不信任模型给的引用 ID**，核验不能再交给模型 |
| finalize 用固定的中英文案渲染，比如"评论无法确认这个问题" | 关键表述不交给模型自由发挥 |
| 节点内降级：plan 失败时用规则代替（标为 `degraded`）；检索、评估或生成失败时 `service_status=failed`、`status=None`，答案明说是服务出错 | 服务故障和"评论无法确认"彻底分开 |
| 提示词里只有问题和这件商品的块 ID 与文本 | 防泄漏 |
| Claude Haiku 5.5，`messages.parse` 加 Pydantic schema，`max_tokens=4096`，不设采样参数；所有失败都统一成 `LLMError` | 评测要跑大量题，用最便宜的模型；统一的错误类型才能在节点里统一降级 |

**为什么用 LangGraph，不直接写函数调用（面试必问）：**
- 有条件分支：超出范围直接结束；评估不可答时跳过生成；需要时改写。
- 有带预算的循环：改写次数记在状态里。
- 状态和追踪：每个节点读写同一份类型化状态，并追加一条 trace，能回查"为什么这样回答"。
- 流式：节点一跑完就能把进度推给前端（第 4 阶段的 `stream_answer`）。

### 5.2 遇到的问题

**问题 3.1（严重）：Claude 回复被截断时，工作流直接崩溃**
- **现象：** 回复在 JSON 中途被截断，或者模型拒答时，`messages.parse` 抛出的是 Pydantic 的 `ValidationError`，不是 SDK 的错误，一路冒出 `answer_question`。
- **为什么测试没发现：** 单元测试里的假 LLM 直接返回已经解析好的对象，根本不经过解析这一步。
- **修复：** 把 `ValidationError` 也包装成 `LLMError`，按服务故障处理（`f5a6cff`）。
- **教训：** 假对象会把集成层的失败藏起来，要专门为"模型返回了不合 schema 的东西"写测试。

**问题 3.2：没有 API key 时 SDK 报的是 `TypeError`**
- **现象：** 实测发现 Anthropic SDK 缺少凭据时，在请求时抛普通的 `TypeError`，按计划只接 `AnthropicError` 是接不住的。
- **修复：** `ClaudeLLM` 先检查 `ANTHROPIC_API_KEY`，没有就直接抛 `LLMError`。
- **代价：** 只靠 `ant auth login` 登录的凭据不会被认，必须设置环境变量。

**问题 3.3：能回答的题被一律降成"部分能回答"**
- **现象：** 真实运行里，3 道能回答的题全部被降成了 partial。
- **根因：** 原规则是"生成步骤列出了未覆盖的内容就降为 partial"。而生成模型总爱写"只有一位评论者提到"这类提醒。
- **修复：** 三态只由证据评估决定；显示给用户的缺口也只来自评估的 `missing` 列表。生成步骤的提醒只记进 trace。
- **为什么：** 单一裁决者。两个模型调用各自对可答性投票，结果会被"更保守的那个"系统性地拉低，而且可答性要能单独检查和改进，裁决权必须集中在一处。
- **代价：** 生成步骤发现、评估漏掉的缺口不会显示给用户。

**问题 3.4：第二次改写可能白花一次调用**
- **现象：** 原计划的候选上限是 2×evidence_k，而且"有没有找到新证据"是在截断之前算的。允许改写 2 次时，第二次改写加不进任何新证据，却会用一模一样的输入再评估一遍。
- **修复：** 上限改为 `evidence_k × (已改写次数 + 1)`，"找到新证据"按截断之后的结果算。
- **代价：** 允许改写 2 次时，提示词最多 24 个块。

**问题 3.5：改写时检索降级，整次运行却没被标成降级**
- **修复：** 改写时的检索如果有一路出错，整次运行标为 `degraded`。同时补测了 4 个原来没测到的分支：检索降级后继续、改写检索失败时保留原候选、读库出错按服务故障处理、`max_rewrites=2` 时不重复用同一个查询。前 3 个测试一写就通过，说明那些分支本来就对；只有降级传播是真 bug。

### 5.3 真实运行（4 道题）

| 题 | 结果 |
|---|---|
| 小商品 "Is it cold pressed?" | 全量上下文，结论"否"，1 条引用，3 次调用，8.5 秒 |
| qid 17020，大商品问音量调节 | 混合检索加重排，7 条引用都属于这件商品，30.5 秒（检索占 19 秒，主要是加载模型） |
| 同一件商品用中文问 | 检索词自动译成英文，回答和固定文案都是中文 |
| "How much does it cost?" | 正确判为不在服务范围，1 次调用，1.9 秒 |

每题成本不到 0.1 美分。17020 暴露了"是非结论和具体结论矛盾"，记录下来留到评测阶段，后来在第 8 节修掉。

## 6. 第 4 阶段：接口、前端、MCP

### 6.1 设计和理由

| 设计 | 理由 |
|---|---|
| 服务启动时只加载一次 BGE-M3、重排模型和 LLM 客户端，并预热 | 命令行每次提问要花约 19 秒加载模型；接口里同一道题从 30.5 秒降到 18.3 秒 |
| `POST /v1/qa` 走 SSE：`run_started` → 每个节点一条 `progress` → `answer_chunk` → `citations` → `done`，异常时发 `error` | 用户看得到"正在检索、正在核验" |
| **答案在引用核验之后才分块发出，不是逐 token 流式**；界面如实说明 | 引用必须先核验再给用户看。逐 token 输出，用户会先看到还没核验的引用 |
| 服务故障也以 `done` 结束，返回 HTTP 200；只有输入错误才返回 4xx（商品不存在 404，问题为空 422） | 服务故障是一种回答状态，不是协议错误，前端要能正常展示它 |
| 每次运行在发出答案之前写入 `qa_runs`；客户端中途断开，后台线程照样跑完并存档 | 可追溯：任何回答都能按 `run_id` 查回来 |
| 工作流在后台线程里跑，全进程一把锁，同时只跑一个问答 | `BM25Cache` 不是线程安全的；CPU 推理并发也快不了。原型阶段的明确取舍，写进了文档 |
| 前端从 Streamlit 换成 Vue 3 + Vite + TypeScript，不用组件库、路由和 Pinia | 真正的网页应用，流式进度、引用高亮这些交互能做细，不受 Streamlit 每次交互都重跑整个脚本的限制，也能作为作品展示。只有一个页面，依赖越少越好 |
| 浏览器用 `fetch` + `ReadableStream` 解析 SSE，不用 `EventSource` | `EventSource` 只支持 GET，问答接口是 POST |
| FastAPI 直接提供打包好的前端，同一个端口 | 演示时不用处理跨域；开发时用 Vite 代理 |
| 徽标逻辑把"服务出错"放在所有答案状态之前判断 | 和检索、工作流同一条原则 |
| MCP 服务只暴露三个只读工具：`list_products`、`search_reviews`、`get_review`；不提供问答工具 | 让外部 LLM 客户端能查证据，和 API 共用查询代码 |

### 6.2 遇到的问题

**问题 4.1：服务端中途断开，页面一直转圈**
- **修复：** 流在没有收到 `done` 或 `error` 时就结束，提示"连接中断，未收到完整结果"。
- **为什么：** 前端只等"成功"或"明确失败"两种结局是不够的，"什么都没收到就断了"是第三种。

**问题 4.2：数据库宕机时，页面让你去启动一个已经在运行的接口**
- **根因：** 健康检查和商品列表放在同一个 `Promise.all` 里，商品接口因为数据库宕机返回 500，整体被当成"接口连不上"。
- **修复：** 健康检查单独发请求，数据库宕机时显示"数据库未连接"。
- **为什么：** 错误提示要指向真正的原因，否则用户会照着错误的提示操作。

**问题 4.3：SSE 事件可能被拆进两个网络分块**
- **做法：** 事件解析器跨分块缓冲，用专门的测试覆盖"一个事件被切成两半"的情况；读流时用 `TextDecoder({stream: true})`，避免多字节字符被切断。

**问题 4.4：Vue 响应式 bug，展开引用后页面不刷新**
- 测试在提交前抓到并修复。

**其他：**
- `mcp` 2.x 把 `FastMCP` 改名成了 `MCPServer`，写计划前先实际确认了接口。
- 服务启动时自动建 `qa_runs` 表，已有的数据库不用手动迁移。
- 运行记录原本没有保存候选和分数，满足不了定位文档 F11"按 run_id 查看候选和分数"的要求；5a 第一个任务补上了。

## 7. 第 5a 阶段：银标评测

### 7.1 设计和理由

| 设计 | 理由 |
|---|---|
| 按"品类 × 银标"分层抽题，固定随机种子 | 可复现，各层都有代表 |
| 片段对齐：先在评论全文里定位片段（忽略空白），再按偏移量映射到块；跨块的片段，两块都算参考证据 | 只看块文本判断不了片段是否跨块；有 3.4% 的片段只有忽略空白才能对上（AmazonQA 的分词在标点两侧加了空格） |
| 少于 10 个非空白字符的片段忽略不计 | 太短的片段在任何评论里都能匹配上 |
| 每道题只检索一次，同时得到 bm25 / dense / hybrid / hybrid_rerank 四种排序 | 省算力，四种方案在完全相同的输入上比较 |
| 全量上下文商品、银标不可答、没对齐上的题都不进分母，分别计数 | 分母要说得清 |
| 某一路出错时，依赖它的混合方案记为空 | 不拿"只有一路的混合"和真正的混合比较 |
| 两个基线：B0 不给证据（看模型会不会想当然地回答），B1 全量上下文（只在混合检索的商品上跑） | 分别回答"检索有没有用"和"检索比全塞进去好不好" |
| 每个指标都附 bootstrap 95% 置信区间（1,000 次重采样）和配对差值；服务故障不计入任何可答性分母 | 不写没有区间的"提升了 X" |
| 逐题结果每完成一行就写盘，重跑时跳过已完成的题 | 断了重跑不会重复花钱 |

### 7.2 遇到的问题

**问题 5.1：检索指标衡量的其实是"像不像 BM25"**
- **发现：** dev 和 test 的每道题都能对齐上约 10 个块，因为片段就是 AmazonQA 自己的 BM25 前 10 条，不管是否真的相关。
- **后果：** 检索指标衡量的是和 AmazonQA 的 BM25 有多一致，天然偏向 BM25；每题约 10 个参考块，Recall@5 最高也只能到约 0.5。
- **处理：** 报告和文档都写明这一点，检索方面的结论留给金标。试跑结果正好印证：test 上"混合 + 重排"比"混合"的 hit@5 低 0.058（95% 区间 [−0.087, −0.029]）。这可能说明重排真的差，也可能只是重排挑出了 BM25 没挑的相关评论，反而被银标扣分；银标分不清这两种情况。后来的金标评测给出了答案：是后一种，金标下混合 + 重排在两个 split 上都最好（9.4 节）。

**问题 5.2（审查发现）：限流导致的失败会被永久记下**
- **现象：** 一道题遇到限流、算作服务故障后，重跑时会被当作"已完成"跳过。
- **修复：** 重跑时，以服务故障或运行出错结束的行会自动重试（`6988e6b`）。
- **为什么：** 断点续跑要区分"跑完了"和"跑了但失败了"，后者是基础设施问题，不是系统的回答。

**问题 5.3（审查发现）：工作流和 B1 不在同一批题上比较**
- **现象：** B1 只在混合检索商品的题上跑，工作流跑了全部 50 题，两者并排放会被误读。
- **修复：** 报告加一行"完整工作流（与 B1 同题）"，只统计 B1 也跑了的题。

**问题 5.4（审查发现）：成本按平均输入量选价格档**
- **现象：** 一次很短的规划调用，加一次 15 万 token 的评估调用，平均下来会落进便宜档，而 B1 最容易遇到这种情况。
- **修复：** 每次调用按它自己的输入量单独定价，`QAResult.usage` 记录每次调用的 token 数。

**问题 5.5：评测跑到一半断网**
- **处理：** 检索评测只用本地模型，可以离线跑；工作流、B0、B1 要调用 Claude，断网后每道题都会变成服务故障。所以先停掉，联网后重跑同一条命令，靠问题 5.2 的重试逻辑补齐。

### 7.3 试跑结果（都是对照银标，不是结论）

| | dev | test |
|---|---|---|
| 检索 hit@5：BM25 / 混合 + 重排 | 0.986 / 0.952 | 0.980 / 0.913 |
| 准确率：工作流 / B1（与 B1 同题时的工作流） | 0.640 / 0.725（0.675） | 0.820 / 0.841（0.886） |
| 每题成本：工作流 / B1 | $0.0010 / $0.037 | $0.0009 / $0.0076 |

- B1 贵主要是因为一件商品：dev 上 B1 花的 $1.28 来自 B00007E7C8 的 4 道题，每题约 64 万输入 token，按长上下文价格计费。这是"大商品不宜全塞进上下文"的成本证据：dev 上工作流的每题成本约为 B1 的 1/37。准确率在金标上分不出高下，见 9.4 节。
- 工作流延迟 P50 约 15 秒，P95 约 30 秒。
- 两个 split 合计花费约 $1.92。

**试跑暴露的三个工作流问题**（第 8 节修复）：
1. 有的题状态是"能回答"，是非结论却是"无法确认"；
2. qid 39526 是英文问题，回答却是西班牙语；
3. "不在服务范围"拒掉了一批银标可答的题，比如保修、尺寸、和别的商品比较。

## 8. 试跑之后的工作流修复（`workflow-fixes` 分支）

这一节最适合在面试里讲"如何调试 LLM 系统"：每次修完都用真实 Claude 重跑，第一版修复没起作用，就继续找原因。

**问题 8.1：可以回答的题在检索之前就被拒了**
- **根因：** 规划提示词把保修、官方规格、比较这些话题直接判成超出范围。试跑里 9 道银标可答的题因此直接被拒。可金标规范第 2 节要求的正好相反：评论里有买家的亲身经历，就按内容判 partial 或 answered。
- **修复：** 只有价格、库存、物流、促销、问卖家本身业务的（"你们卖不卖""寄不寄到"）、请系统推荐别的商品、医疗或法律上的确定性判断，这几类直接判出范围；保修、规格尺寸、适配、真伪、比较都进入检索，由证据评估判断。定位文档同步修改。
- **为什么：** 范围判断只能拦"评论原则上不可能回答"的题；"评论里有没有"必须看过证据再说，那是评估节点的职责。
- **验证：** 原来在检索前被拒的 16 道题重跑，只剩 46285（"ENVIA A VENEZUELA"，问能不能寄到委内瑞拉）还被拒；其余 15 道进入检索，得到 4 道能回答、10 道部分、1 道不能回答，答案都有实质内容。

**问题 8.2：英文问题被回答成西班牙语**
- **根因：** 提示词要求"用提问的语言回答"。39526 是一句不通顺的英文，被模型当成了西班牙语。
- **修复：** 由代码判断问题里有没有中文，在每个提示词里写一行固定的 `Answer language: Chinese|English`。
- **为什么：** 系统的固定文案只有中英两种，模型写的内容必须和它保持同一种语言。这个判断应该由确定性的代码来做，不该交给模型。

**问题 8.3：状态和是非结论不一致，修了三轮**
- **第一轮：** 把 `unknown` 从生成的输出格式里删掉。理由是只有 answered/partial 才会走到生成，这时不该说"无法确认"。**真实重跑后仍然失败：** 5609 的生成结果根本没给结论，系统补成了 unknown，还是 partial + unknown。
- **第二轮：** 把结论设为必填。**出现新的错误：** 5609 变成了"Yes"，可唯一的证据是一位评论者*担心*这个产品做过动物实验。模型被逼着选边，把担忧当成了证据。
- **第三轮（最终）：** 是非题用单独的输出格式 `GeneratedYesNoAnswer`，结论必填，但允许 `unknown`（证据不偏向任何一边）；核验时一旦看到 `unknown`，就把整次运行降为不可答。这样从结构上保证 `unknown` 只会和 unanswerable 一起出现。提示词补充：相近情形（别的年款、相似尺寸）仍要偏向是或否，并在结论里说明是相近情形；评论者的担心或猜测不算证据。
- **为什么：** 不一致的根源是"生成说不确定，评估说能答"两个判断各说各的。最终方案既不强迫模型乱选，也不让矛盾的组合到达用户，矛盾由确定性代码按固定规则收敛。

**问题 8.4：多问句的是非题结论答错了问题**
- **现象：** 21567 问 "Does it come with the weight? If not, do you sell one?"，回答说配重要另外买（也就是"不包含"），结论却是"Yes"。模型回答的是第二问。
- **第一次尝试：** 只在提示词里加例子，仍然得到 "Yes"。
- **修复：** `GeneratedYesNoAnswer` 的第一个字段是 `verdict_question`：模型要先写下它的结论回答的是哪一个是非问题，最后才写 `verdict`。这个问题会记进 trace。
- **为什么：** 结构化输出按 schema 的字段顺序生成，字段顺序就是模型的写作顺序。先写下"我在回答哪一问"，相当于让模型先承诺再作答，而且事后能检查。
- **一个实现细节：** Pydantic v2 的子类字段排在父类字段之后，所以 `GeneratedYesNoAnswer` 写成独立的模型，不继承 `GeneratedAnswer`，否则 `verdict_question` 没法排在最前、`verdict` 也没法排在最后。有测试检查 schema 的第一个和最后一个字段。
- **验证：** 21567 跑了 3 次，模型都写下了第一问；结论两次 "No"、一次 "Can't confirm"，没有再出现 "Yes"。"Can't confirm" 也说得通，因为没有评论直接说不包含配重。

**问题 8.5：把"评论没提到"写成带引用的结论**
- **现象：** 出现了 "the excerpts do not state the warranty [1]" 这类结论：引用了一条评论，来证明评论里*没有*某样东西。
- **修复：** 提示词规定，结论只能转述评论者说了什么；评论没提到的内容进 unknowns，不能写成结论。
- **验证：** 54504（保修）现在直接判为不可答；45546（流明）和 39421（尺寸）缺的数字出现在"评论没有提到"那一栏。

**关于 LLM 的不确定性：** 每道题只跑了一到三次，同一道题两次运行的结果也可能不同（39526 就翻转过）。所以这些重跑只能说明修复的方向对，稳定的数字要看金标评测。真实调用合计约 $0.35。

## 9. 第 5b 阶段：金标

### 9.1 设计和理由

| 设计 | 理由 |
|---|---|
| **子 agent 预标、人逐题审核**，而不是直接用子 agent 的标注 | 金标的意义在于"人核对过"。被测系统用 Claude，标注也用 Claude，同一家模型容易在同一类题上犯同样的错，系统的错会被判成对，准确率偏高，而且偏多少看不出来 |
| 200 题，dev 100 + test 100 | dev 用来调试和分析错误，test 只用来出最终数字 |
| 40 道盲标题：人先独立判断，提交后才能看到预标 | 只有一位人工标注者，没法做双人标注；用盲标和预标的一致率代替，报告里照实写，不说成双人标注 |
| 候选池 = 四种检索方案各自前 10 条的并集，按块编号排序展示 | 用题目原文检索，不依赖被测系统的改写查询；排序不暴露哪个方案排得靠前，避免标注偏向某个方案 |
| 标注者可以在这件商品的全部评论里搜索候选池之外的块 | 不让候选池的漏召回变成"不可答"标签 |
| 子 agent 只能通过 `packet` 和 `search` 两个命令读数据，看不到银标、片段和社区回答 | 防泄漏 |
| 证据分 0/1/2 三级；answered/partial 至少要有一个 2 级块，unanswerable 不能有 2 级块；`unknown` 当且仅当 unanswerable | 规则能被代码校验 |
| 审核接口只有设了 `REVIEWPROOF_ANNOTATION=1` 才开启，只监听本机 | 本地工具，默认关闭 |
| 金标评测：三态混淆矩阵、是非题结论准确率、B2（AmazonQA 自带分类器）、各种一致率、按评论量分档对比工作流和 B1 | 分档对比为调全量上下文的阈值提供依据 |

### 9.2 遇到的问题：重新分级的原则

整体审查报了 1 个重要、10 个次要问题。我按**实际影响**重新分级：**凡是会让未经审核或错误的标注悄悄变成金标的，一律算重要**，因为它会让"人工审核"这件事失去意义。

| 问题 | 修复 |
|---|---|
| 按住或连按 Ctrl+Enter 会跳过题目，把预标直接存成终审 | 保存中、按键重复、刚打开题目 0.5 秒内都不响应 |
| 按 Cmd/Ctrl+1–3 时会顺带改掉可答性 | 带修饰键的数字键不再改可答性 |
| 没有预标的题，所有块都被折叠成"预标为无关"，默认 0 分 | 没有预标时全部展开 |
| 已经有人工标注后，预标仍能被覆盖，会污染一致率 | 有人工标注后拒绝再写入预标 |
| 预标文件格式不对时导入中途崩溃；等级为 `true` 会被存进去（Python 里 `True == 1`） | 逐行校验，拒绝布尔值和非对象行 |
| 在搜索框里按 Ctrl+Enter 会同时触发搜索和保存 | 只保存 |

**审核开始前又修的四处**（`909c5e6`）：
- "下一道待审"不管当前筛选，会跳到筛选之外的题。现在只在筛选结果里找。
- 候选池里的块在数据库里找不到时，会被悄悄丢掉。现在页面顶部会显示红色警告，并且这道题保存不了。
- 已有标注时重新导入数据，会抛出一长串外键错误。现在整批回滚，以退出码 2 结束，并给出一句中文说明。
- `load_gold` 原来只检查 `dataset_id` 在数据库里存在；现在要求它就是这道题所属商品当前的数据集。

**子 agent 预标中发现的问题：**
- 第 14 批的子 agent 写的辅助脚本，把没逐一列出的块都默认标成了 0。
- 43891 把候选池里每一块都标成了 2。

两处都记进了 `review-notes.md`，审核时重点看。

### 9.3 审核结果

- 200 题全部经过人工审核，改动了 8 题（4%）：1 题可答性（87889，answered 改为 partial），1 题是非结论（28306，mixed 改为 yes），6 题证据等级（共 27 块 2→1、2 块 1→0、1 块 1→2，主要是 43891 和 9073 两题，各改 13 块）。
- 盲标：40 题里人和预标的可答性一致 34 题（dev 15/20，kappa 0.593；test 19/20，kappa 0.919）。6 道分歧题终审都采用了预标的结论。
- 最终分布：answered 109、partial 48、unanswerable 43；2 级证据块 881 个。
- **怎么解读：** 金标和预标非常接近。可能是预标本来就准，也可能是看过预标后被锚定，两者分不清。所以金标的准确说法是"Claude 子 agent 预标、一位人工逐题审核"，不是独立的人工标注。

### 9.4 金标评测结果

两个 split 各 100 题。完整工作流、B0 每题都跑；B1 只在混合检索商品的 70 题上跑；B2 直接拿银标当预测。合计花费 $3.01（dev $2.12，大头是 B1；test $0.89）。没有服务故障，也没有越界引用。均值后的方括号是 95% 置信区间。

| | dev | test |
|---|---|---|
| 检索 hit@5：BM25 / 向量 / 混合 / 混合 + 重排（dev 56 题、test 62 题） | 0.679 / 0.821 / 0.786 / 0.893 | 0.742 / 0.790 / 0.774 / 0.855 |
| nDCG@5 配对差值：混合 + 重排 − BM25 | 0.211 [0.135, 0.286] | 0.238 [0.148, 0.318] |
| nDCG@5 配对差值：混合 + 重排 − 混合（重排本身的作用） | 0.138 [0.068, 0.212] | 0.132 [0.074, 0.192] |
| 可答性准确率（答或拒是否正确）：工作流 | 0.850 [0.780, 0.910] | 0.830 [0.750, 0.900] |
| 可答性准确率：B0 不给证据 / B2 AmazonQA 分类器 | 0.300 / 0.780 | 0.250 / 0.780 |
| 同一批 70 题的可答性准确率：工作流 / B1 | 0.843 / 0.929 | 0.814 / 0.743 |

**怎么读：**
1. **检索：银标试跑的结论反过来了。** 银标下 BM25 的 hit@5 最高；金标下混合 + 重排在两个 split 上都最好，nDCG@5 比 BM25、比不重排的混合都高，区间不跨 0。hit@5 比 BM25 的差值在 test 上是 0.113 [0.000, 0.226]，下限刚好碰到 0，所以说"重排提升了排序质量"用 nDCG 更稳妥。这印证了问题 5.1：银标衡量的是和 AmazonQA 自己的 BM25 一致的程度。
2. **可答性：** 工作流远好于不给证据的 B0，说明它确实用上了检索到的证据，而不是凭常识回答。点估计高于 AmazonQA 分类器 B2，但区间重叠，也没做配对检验，不能说显著更好。
3. **工作流 vs B1：** dev 上 B1 更高，test 上工作流更高，区间都重叠，两个 split 方向相反，这个样本量下分不出高下；成本差一个数量级（dev 约 27 倍，test 约 10 倍）。按评论量分档，B1 也没有在哪一档稳定领先，所以暂不改 6,000 token 的全量上下文阈值。
4. **主要弱点：** 一是误拒，dev 11 题、test 14 题，其中多数是金标为 partial 的题被判成不可答（dev 8 题、test 9 题）；二是是非题结论准确率只有五成多，题少、区间宽，但这是下一步最该改的地方。针对误拒的修复试过一轮，没有成立，见 9.5 节。
5. **口径：** dev 是修 workflow 时参考过的集合，数字可能偏乐观；test 上也有一道试跑错题（21567）用于改提示词，那道题不在金标里。

### 9.5 金标之后的误拒修复：一次没有成立的修复（`refusal-fixes` 分支）

这一节适合在面试里讲"怎样用评测做决定"：按错误分析改了三处，在 dev 上验证，发现只是把误拒换成了误答，于是全部回滚，test 没有复跑。计划见 `docs/superpowers/plans/2026-10-29-refusal-fixes.md`。

**起点：9.4 节的 25 道误拒（dev 11、test 14），逐题看原因。**
- 11 道：评估判能答或部分能答，但生成给了 `unknown` 结论，核验按问题 8.3 的规则把整题降为不可答；
- 11 道：评估直接判不可答，多数只有相近情形的证据（别的年款、别的用法），规范第 2 节算 partial；
- 3 道：规划判成超出范围，例如 dev 73170 问这款保护套选哪个尺码，被当成"推荐别的商品"。
- 25 道里有 22 道是预标子 agent 在 `review-notes.md` 里列为边界情况的题；全部 157 道可答题里，这个比例是 52%。

**三处修改（只参考 dev 和标注规范）：**
1. `unknown` 结论不再把整题降为不可答，只降为部分可答，引用的结论作为相关证据显示；
2. 评估提示词按规范第 2 节改写：一位评论者的亲身经历就够 answered，意见分歧也算 answered，只有相近情形算 partial，完全不沾边才算 unanswerable；
3. 规划提示词：问"这款商品哪个尺码或型号适合我的东西"不算推荐别的商品，进入检索。

**dev 结果（100 题，只跑工作流；两次复跑合计 $0.23）：**

| | 修复前 `gold-dev` | 三处都改 `gold-dev-r2` | 回滚第 1 处 `gold-dev-r3` |
|---|---|---|---|
| 可答性准确率（答或拒是否正确） | 0.850 [0.780, 0.910] | 0.850 [0.770, 0.920] | 0.850 [0.770, 0.920] |
| 误拒 / 误答（题数） | 11 / 4 | 4 / 11 | 8 / 7 |
| 误拒率（77 道可答题） | 0.143 | 0.052 | 0.104 |
| 正确拒答率（23 道不可答题） | 0.826 | 0.522 | 0.696 |
| 三态完全一致 | 0.710 | 0.670 | 0.700 |
| 是非题结论准确率（12 题） | 0.583 | 0.500 | 0.583 |

**为什么没有成立：**
1. **只分析了一类错误。** 造成误拒的规则同时也在挡误答。r2 里"部分可答 + 结论 `unknown`"的 9 题，金标可答 4 题、不可答 5 题，这个信号分不开两类题。规则一放松，两类错误一起动，总数不变。
2. **规则被模型推广了。** 评估提示词里的"相近情形（别的年款或尺寸、类似用途）"被用到了别的设备型号上：问 Camry 的雾灯，拿 Venza 和 Accord 的评论答"是"；问 Inspiron 1525 的内存，拿别的 Inspiron 型号作答。和修复前比，r3 新增的 5 道误答里有 3 道是这种情况。规范里的相近情形，是同一辆车的另一个年款。
3. **错误集中在边界题上。** 见上面的 22/25：系统出错的地方，多半就是预标时已经觉得两种判法都说得通的题。改提示词很难只把它们往对的方向推。
4. **效应小于噪声。** 每处修改只针对几道到十来道题，而 dev 只有 100 题，准确率区间宽约 ±0.07。r2 和 r3 的规划和评估提示词完全相同，2932、53648、83254 三题的评估结论却从不可答变成了部分可答，成了误答。这是 LLM 两次运行之间的随机差异：2932 和 83254 两次评估的输入 token 数完全相同，53648 是规划写的检索词不同。这种差异和修复本身的效应一样大。

**决定：** 三处修改全部回滚（`e022560`、`9535003`），工作流代码和 9.4 节测过的版本完全相同，gold-test 的数字仍然有效。test 没有复跑，留给在 dev 上真正有提升的版本。第 3 处修改单看是对的（73170 两次都修好了），但 r2、r3 两次都把 18315（"do you have bags…"）判成问卖家（预标时也注明它像问卖家库存），所以一起回滚。留下的只有几条单元测试断言，它们固定的是原来的规则。计划里事先写好的停止条件（新增误答多于修好的误拒就不跑 test）在 r3 刚好卡在边上（5 对 5），最后按产品原则（宁可拒答，不编答案）决定不跑。

**教训：**
- 只看一类错误做分析，修复很可能只是在同一条取舍曲线上移动位置，而不是把曲线整体往外推。改之前要估计它会放进来多少另一类错误。
- 要在误拒和误答之间做取舍，更好的办法是有一个输出连续分数的可答性判断：在 dev 上画出两类错误随阈值变化的曲线，明确选一个点，再在 test 上测一次。第 6 阶段检查过现成的重排分数能不能充当这个分数，答案是不能（第 10 节）。
- 想验证几题规模的改动，评测本身要更有力：同一版本多跑几次，对翻转的题做配对检验（如 McNemar），或者扩大题量。

## 10. 第 6 阶段：检查之后，决定不训练可答性模型

### 10.1 原计划和先做的检查

原计划（路线图第 6 阶段）是用 AmazonQA 训练集的银标微调一个交叉编码器，输出可答性分数，在金标 dev 上选阈值，替换或对照 LLM 证据评估。动手训练之前，先做了一个不训练、不调 Claude 的检查：现成的重排模型给出的最高分，能不能区分可答和不可答的题？如果同类模型现成的分数都分不开，训练一个也很难把误拒修好。

做法（`python -m reviewproof.eval.rerank_check`，报告 [rerank-check-dev](../reports/eval/rerank-check-dev/report.md)）：金标 dev 的 100 题，打分范围和系统一致（全量上下文商品给每个块打分，混合检索商品给重排池的 40 个块打分），用题目原文当查询，拿最高分和金标可答性比较（answered、partial 算可答），再和同一批题上的工作流、B2 比较。只用 dev，test 没有动。

### 10.2 结果

| dev（100 题） | |
|---|---|
| 最高分区分可答和不可答的 AUC | 0.802 [0.689, 0.892] |
| 只看最高分的准确率（阈值在同一批题上挑的，偏乐观） | 0.830 |
| 准确率：工作流 / B2 / 全部判可答 | 0.850 / 0.780 / 0.770 |
| 工作流拒答的 30 题里，最高分区分误拒（11）和正确拒答（19）的 AUC | 0.608 [0.364, 0.837] |

**怎么读：**
1. **分数有信号，但不够用。** 它衡量的主要是评论有没有谈到这个话题。只看分数定阈值，准确率也不如现在的工作流，何况这个阈值是在同一批题上挑的。
2. **它修不了误拒。** 最高分 ≥ 0.3 的拒答题只有 4 道，其中 3 道是误拒，例如 27383 问能不能挂在衣柜杆上，排第一的评论（0.58 分）就说挂在了衣柜杆上：模型手里有证据，却判错了。其余误拒的最高分很低，支持的评论比较间接，或者根本不在打分范围里。
3. **难点在 partial 的边界。** 11 道误拒里 8 道金标是 partial，评论说的是相近情形，例如问 2015 款 Wrangler 能不能装，评论说 2014 款装上了（1505，最高分 0.96，系统拒答）。这要读内容判断，分数给不了。
4. **分数高也不代表能回答。** 误答 65508 的最高分是 0.93：评论提到了提问者问的那款竞品，但没有拿两者比较。

### 10.3 决定：不训练

可答性继续由 LLM 证据评估裁决。理由：
- **训练数据的上限低。** 银标就是 AmazonQA 分类器的输出，把它当预测（B2）在金标上只有 0.780，低于现在的工作流；拿银标训练，学到的最多是这个分类器。金标只有 200 题，test 还要留作评测，不够训练。
- **检索分数里没有要学的信息。** 误拒集中的 partial 边界要读内容判断，上面的检查说明分数分不开。
- **个人项目的取舍。** 这个项目的重点是讲清楚每个模块为什么这样设计。这次检查本身就是"可答性由 LLM 判断"这个设计的依据（见文末体检表），做到这里停下，比训练一个上限不高的模型更划算。

可以做、但没有排期的改进写在第 13 节。

## 11. 贯穿始终的原则（面试时可以总结成这几条）

1. **服务故障 ≠ 评论无法确认。** 检索层的 `service_status`、工作流的 `status=None`、接口的 `done` 事件、前端的徽标优先级、评测分母，每一层都单独表示故障。这是整个系统最重要的不变量，第 2 阶段审查的唯一重要问题就是它。
2. **不信任模型输出，用代码核验。** 引用 ID 由代码核验；语言由代码决定；`unknown` 和 unanswerable 的对应关系由代码强制保证；模型返回不合 schema 时按服务故障处理。
3. **单一裁决者。** 可答性只由证据评估决定，不让多个模型调用各自投票。
4. **防泄漏。** 社区回答、片段和标签只存在 `questions` 表，有测试检查它们不会进入任何提示词；标注子 agent 也看不到它们。
5. **结论要克制。** 银标和金标、系统 ID 和 Amazon ID、BM25 一致度和真实相关性，文档里都严格区分；没有置信区间就不写"提升"。
6. **先写失败的测试。** 每个修复都先有一个会失败的测试；修完后再用真实运行验证，因为假 LLM 会把集成层的问题藏起来（问题 3.1）。
7. **按实测推翻判断。** MPS 的修复、审查代理的结论、我自己的第一版是非题修复、金标之后的误拒修复（9.5 节），都是因为实测结果不对才推翻的。
8. **按影响分级，不按"规格里有没有写"。** 第 1 阶段测试可能清空正式库、第 5b 阶段会悄悄产生错误金标的几个问题，审查时都被评为次要，我按实际影响提为重要并修复。

## 12. 面试常见追问

**Q：为什么不直接把所有评论塞进长上下文？**
小商品确实这么做（100 件里有 28 件）。大商品试过（B1）：dev 上一件 22 万 token 的商品每题约 64 万输入 token。金标上同一批 70 题，dev 上 B1 的准确率点估计更高（0.929 对 0.843），test 上工作流更高（0.814 对 0.743），区间都重叠，分不出高下；而 B1 的每题成本约是工作流的 27 倍（dev）和 10 倍（test）。证据太多时，引用也会变得含糊。

**Q：为什么用 RRF，不用加权融合？**
两路分数的量纲不同（余弦相似度和 BM25 分数），加权要调参，而且换个商品就可能失效。RRF 只看名次，k=60 是常用默认值。

**Q：为什么不建 HNSW 等 ANN 索引？**
检索永远限定在单件商品内，最多约 9,000 条评论，精确排序足够快。先过滤再走 ANN 反而会损失召回。

**Q：重排在评测里分数更低，说明重排没用吗？**
不能这么下结论。银标的参考证据是 AmazonQA 自己的 BM25 前 10 条，越像 BM25 的排序得分越高，重排挑出 BM25 没挑到的相关评论，反而会被扣分。换成人工金标后结论反过来了：混合 + 重排在 dev 和 test 上 nDCG@5 都最高，比 BM25 高 0.211 [0.135, 0.286] 和 0.238 [0.148, 0.318]，比不重排的混合高约 0.13，区间都不跨 0。

**Q：怎么防止模型编造？**
三层：提示词里只有这件商品的评论块；生成的每条结论都必须带块 ID，由代码核验，不在候选里的引用删掉，没有引用的结论删掉；评估判为不可答时根本不调用生成，直接输出固定文案。

**Q：为什么用最便宜的 Haiku？**
评测要跑成百上千次调用；每题成本约 $0.001。结构化输出加代码核验，弥补了小模型的不稳定。

**Q：为什么是"子 agent 预标、人审核"，不直接让 LLM 标？**
见第 9 节：同一家模型给自己判卷，错误相关，准确率会偏高而且看不出偏了多少。预标让人审核快很多（每题约 1–2 分钟），每道题仍然有人确认过。盲标题还能量化子 agent 和人的一致率。

**Q：LLM 输出不稳定，你怎么判断修复有效？**
每次修完用真实 Claude 重跑出问题的题；关键题跑多次（21567 跑了 3 次）；如实说明这只能证明方向对，稳定的数字看金标评测（9.4 节：可答性准确率 dev 0.850、test 0.830）。另外尽量把要求变成结构上的保证：`unknown` 只会和 unanswerable 一起出现是由核验代码强制的，不靠模型自觉。反过来也要承认评测的分辨力有限：9.5 节里同样的提示词跑两次，有 3 题结论不同，和一次修复的效应一样大，所以几题规模的改动，单跑一次分不出来。

**Q：有没有做过但没成功的优化？**
有，见 9.5 节。金标暴露了误拒问题，我按 25 道误拒题的分析改了三处提示词和规则。dev 上误拒从 11 题降到 4 题，误答却从 4 题升到 11 题，准确率不变（0.850）；回滚其中一处后是 8 和 7，仍然是 0.850。我判断这只是在误拒和误答之间换位置，于是全部回滚，没有拿 test 去测一个在 dev 上没有提升的版本。教训是错误分析要同时看两类错误；真要调这个取舍，需要一个输出分数的可答性判断。第 6 阶段检查过重排模型的分数，它分不开误拒和正确拒答，所以没有继续训练模型（第 10 节）。

**Q：并发怎么处理？**
原型阶段全进程一把锁，同时只跑一个问答，因为 BM25 缓存不是线程安全的，CPU 推理并发也快不了。这是写进文档的明确取舍。要扩展的话，可以把 BM25 索引按进程隔离，或者换成 Postgres 全文检索，模型推理放到 GPU 服务上。

## 13. 已知局限和还没做的

**金标评测暴露的弱点（9.4 节）：**
- 误拒：金标可答的题被判为不可答，误拒率 dev 0.143、test 0.175，多数是金标为 partial 的题；
- 是非题结论准确率只有 0.583（dev 12 题）和 0.533（test 15 题）；
- 试过用提示词和规则修误拒（9.5 节），dev 上三次都是 0.850，只是把误拒换成了误答，已全部回滚。

**还没做（没有排期）：**
- 评测的分辨力：同一版本多次运行、对翻转的题做配对检验，或扩大金标题量；
- 评估时采样几次再投票，用上一条的方法检验它有没有用；
- 拒答时如果重排分数高，附上最相关的几条评论，让用户自己判断（不改可答性判定）；
- 中文提问小题集、结论支持率（逐条核对引用）、是非题结论和社区回答的一致率；
- 全量上下文阈值（6,000 token）还没有专门调过；金标的分档对比里 B1 没有在哪一档稳定领先，暂时没有提高它的依据。

**已知的小问题（记在各阶段台账里，暂不处理）：**
- 检索中途数据库连接断开时，回滚本身也可能报错，导致异常直接抛出；
- BM25 缓存的键是块数和总长度，长度不变的文本修改要重启才能生效；
- 引用高亮的偏移量是 Python 的码点，前端按 UTF-16 截取，带 emoji 的评论会偏移；
- 取消提问后，服务端仍会把那次运行跑完；排队请求太多会占满线程池；
- 出错事件里带有原始的异常文本，部署前要处理；
- 商品没有名称：后来按 ASIN 补上了全部 100 件的标题，先查 Amazon Reviews 2023 元数据（找到 50 件），缺的再查 2014 年的 Amazon 商品数据（补齐其余 50 件）。
