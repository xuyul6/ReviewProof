# 项目定位：购前单商品评论问答

日期：2026-10-27。状态：定位稿，已选定方案 A。

本文回答"做什么、给谁用、做到什么程度、不做什么"。具体怎么改、分几个阶段，见 [改动方案](roadmap_cn.md)。本文的功能和指标都是目标。"当前状态"一栏记录的是 2026-10-27 拆分前旧系统（主链路和小样本演示，现在留在旧仓库 [xuyul6/BRIDGE](https://github.com/xuyul6/BRIDGE)）的情况，本仓库不含这些代码。

## 1. 一句话定位

**用户选定一件商品后，系统用这件商品的买家评论回答具体问题：能答时给出带引用、可回查的结论；评论不足以回答时明确说"评论无法确认"，而不是编造。**

核心卖点是**可答性判断**：该答的答、该拒的拒、只能部分回答时说清楚哪部分能确认。这一点可以用 AmazonQA 的可答性标签和人工金标量化，是本项目区别于"又一个 RAG 聊天框"的地方。

## 2. 痛点、场景与使用时机

### 2.1 痛点

| 痛点 | 现状 | 本系统的做法 |
|---|---|---|
| 商品描述不写真实使用体验 | 兼容性、实际尺寸、耐用度、噪音等只有买家知道 | 只用该商品的评论作证据 |
| 评论太多，翻不完 | 热门商品有成百上千条评论，相关的可能只有几条 | 检索 + 重排，把相关评论找出来 |
| 社区问答要等，经常没人答 | 需要等其他买家回复 | 即问即答，引用已有评论 |
| 通用大模型会"想当然" | 只给商品名时，模型会按常识或其他商品编一个答案 | 没有证据就拒答，结论必须挂引用 |

### 2.2 适用场景与使用时机

用户在商品详情页、**下单前**，心里有一个**具体问题**，想知道"买过的人怎么说"。典型问题：

- 兼容/适配：这个充电器能给 2019 款 MacBook Pro 充电吗？这款脚垫适合某车型吗？
- 尺寸/规格的实际体验：鞋码偏大还是偏小？实际容量够一家四口吗？
- 使用体验：运行噪音大吗？敏感肌用了会不会过敏？
- 耐用/故障：用半年后会不会出现某个问题？
- 是非题：能不能放进洗碗机？防不防水？

### 2.3 不适用的问题（识别后引导，不硬答）

价格、库存、物流、促销；需要以官方为准的规格参数；售后与退换政策；跨商品对比和推荐；医疗、安全类的确定性判断。这类问题评论回答不了，或不应该由评论回答，详见第 7 节。

## 3. 用户流程

1. 选择品类，再搜索或选择商品。界面显示商品名、已收录评论数和数据来源。
2. 输入问题，看到检索进度。
3. 得到回答，标明状态：**可答 / 部分可答 / 评论无法确认**；是非题另给结论。
4. 点开结论旁的引用编号，查看原评论。
5. 需要时查看本次运行详情：检索到了什么、为什么这样回答、哪里降级了。

## 4. 功能清单

优先级：**P0** 是定位成立的前提，**P1** 是完整体验，**P2** 是加分项。

| # | 功能 | 验收标准 | 优先级 | 当前状态 |
|---|---|---|---|---|
| F1 | 商品目录与选择 | 按品类筛选商品，显示商品名、评论数、来源；未选商品不能提问 | P0 | 小样本有 3 件商品；主链路只有 `file_id`，没有商品概念 |

## 5. 数据方案

### 5.1 已核实的数据事实

AmazonQA（[仓库](https://github.com/amazonqa/amazonqa)、[论文 arXiv:1908.04364](https://arxiv.org/abs/1908.04364)）：

- 约 92.3 万问题、360 万社区回答、1400 万条评论、15.6 万件商品、17 个品类；按商品切分 train/val/test，同一商品的问题不会跨集合。
- `review_snippets`：评论按约 100 词切成片段后，**按问题用 BM25 排序取前 10**。
- `is_answerable`：**逻辑回归分类器的输出**，不是逐题人工标注。论文中该分类器在 137 条测试样本上精确率 0.67、召回率 0.83、F1 0.74。它是"银标"，而且是相对于该题的 10 个片段判定的。
- 另提供按商品组织的原始文件：`val-qar_products.jsonl`（731,873,701 字节）和 `train-qar_products.jsonl`（约 5.95 GB）。README 没有说明它们的字段结构，下面 5.3 节是我们自己核实的结果。

本地 `data/val-qar.jsonl`（验证集）统计：

| 项 | 数值 |
|---|---|
| 问题 / 商品 / 品类 | 92,183 / 15,592 / 17 |
| `is_answerable=1` 占比 | 64%（是非题 65%，描述题 64%）；Automotive 最低，为 50% |
| 每件商品问题数 | 中位数 6，P90 为 9；≥5 题的商品 10,342 件，≥10 题的 1,177 件 |
| 每件商品去重后的片段数 | 中位数 25，P90 63，最多 100 |
| 每件商品片段总长度 | 中位数约 7,500 字符（约 1,900 tokens），P90 约 24,000 字符（约 6,000 tokens） |

### 5.2 关键判断：检索语料不能只用 `review_snippets`

1. **规模太小，检索体现不出价值。** 把一件商品的所有片段整池放进上下文，P90 也只有约 6,000 tokens，直接塞给大模型就行，用不着混合检索和重排。
2. **评测会偏向 BM25。** 片段本身就是 BM25 按题选出来的，用它比较 BM25 和向量检索，结果天然偏向 BM25。
3. **可答性标签只对片段成立。** `is_answerable` 是基于那 10 个片段判定的。换成完整评论后，部分"不可答"的题可能变成可答，银标需要重新核验。

### 5.3 已确定的语料：`val-qar_products.jsonl`

2026-10-27 已下载到 `data/`（不进 git），SHA-256 为 `866095e6cce9abe5bc142e0ff1326737d57b5f24b19670123c6006d618bd941f`。核实结果：

| 项 | 结果 |
|---|---|
| 记录结构 | 每行一件商品：`asin`、`category`、`questions`（`questionText`、`questionType`、`answers`）、`reviews`（只有 `reviewText` 和 `helpful` 投票数） |
| 规模 | 15,606 条商品记录，1,403,958 条评论，无坏行 |
| 每件商品评论数 | P10 为 4，中位数 31，P90 为 203，P99 为 909，最多 8,966 |
| 每件商品评论总量 | 中位数约 2,800 tokens，P90 约 22,000，P99 约 104,000（按 4 字符 ≈ 1 token 估算） |
| 每件商品问题数 | 中位数 6，最多 10 |
| 单条评论长度 | 中位数 238 字符，P90 为 878 字符 |
| 与 `val-qar.jsonl` 的对应 | 92,373 条问题全部能按 `asin` + 问题文本对上，`qid` 和 `is_answerable` 由此取得 |
| `review_snippets` 能否在完整评论中原文找到 | 随机 1,500 件商品中 97.3%（78,495 / 80,690）能找到 |
| 重复 | 完全相同的评论文本平均占比 0.02%；少量 ASIN 出现在多条记录中（至少 13 个），入库时需要合并 |

**结论：**

1. **直接用这个文件作语料。** 它与问题同源、同一批 ASIN，不需要再找 McAuley 2014 或 Amazon Reviews 2023 做跨数据集对齐。
2. **评论没有原生 ID、评分和时间。** 稳定 ID 用"文件 SHA-256 + ASIN + 评论在该商品中的序号"生成，界面上称为"系统评论 ID"，不能称为 Amazon 评论 ID。
3. **片段可以对齐到具体评论。** 97% 的片段能在完整评论中原文找到，所以可以用片段所在的评论作为 qrels 的候选相关项，再交给人工核查。剩下 3% 不能自动对齐，需单独处理，不能丢弃不报。
4. **检索只在评论多的商品上有意义。** 一半商品的全部评论不到约 3,000 tokens，直接放进上下文就行。超过 200 条评论的商品（约前 10%）全部评论在 2 万 tokens 以上，混合检索和重排才有发挥空间。因此抽样要有意多选评论多的商品，并始终和"全部放进上下文"（6.5 节 B1）对比。
5. **商品名仍然缺失。** 这个文件里没有商品标题，需要从商品元数据补全；补不到时显示 ASIN，不生成猜测的名称。

### 5.4 抽样

- **品类（建议 4 个）：** Electronics（兼容和参数题多）、Home_and_Kitchen（尺寸和使用题多）、Automotive（可答比例最低，适合考验拒答）、Beauty（体验和肤质题多，同时考验安全类问题的克制）。
- **商品：** 每个品类取 25 件、共 100 件，条件是问题 ≥5 个，并按评论数分层：≥200 条 10 件、50–199 条 10 件、<50 条 5 件。有意多选评论多的商品，让检索有难度。同品类的 25 件商品互为干扰项，用来测试商品隔离；按标题挑选"相近商品"要等补全商品名之后再做。
- **可选数量：** 满足"问题 ≥5 且评论 ≥200"的商品，Electronics 有 396 件，Home_and_Kitchen 234 件，Beauty 47 件，Automotive 只有 21 件。Automotive 评论普遍少（中位数 11 条），如果凑不满就从 50–199 层补，并在 manifest 中记录。
- **问题：** 这些商品下的全部问题，约 600 题。
- **切分：** 在 AmazonQA 验证集内部按商品再分 dev（约 30%，用于调参和定阈值）和 test（约 70%，冻结，正式结果只跑一次）。
- 固定随机种子，保存抽样清单（manifest）和文件校验值；不截取大文件的前 N 行。

规模是起步建议，数据核实后可以调整，但调整也要通过 manifest 记录。

### 5.5 防泄漏规则

- `questionText`、`answers`、`is_answerable` 永远不进入检索索引，也不进入生成提示词。
- 评测运行时关闭 F14（相似历史问答），因为同一商品其他问题的社区回答可能直接包含本题答案。
- 阈值、融合权重、重试次数只在 dev 集上调。

### 5.6 人工标注

- **可答性金标：** 从 test 集分层抽约 200 题（品类 × 题型 × 银标正负），由人根据"该商品的评论池"判为 可答 / 部分可答 / 不可答。20% 的题双人标注，报告一致率；同时报告金标与 AmazonQA 银标的一致率。
- **支持证据（qrels）：** 对可答题，把各检索方案前 K 名候选合并成候选池，由人标注哪些证据直接支持答案。不可答题不编造相关 ID。
- **是非题结论：** 对金标集里的是非题，人工根据评论给出 是 / 否 / 意见不一。社区回答只作为弱参考，单独报告。

## 6. 评测指标

### 6.1 核心：可答性

| 指标 | 定义 |
|---|---|
| 正确拒答率 | 金标"不可答"的题中，系统输出 `unanswerable` 的比例 |
| 误拒率 | 金标"可答"的题中，系统输出 `unanswerable` 的比例 |
| 三态宏 F1 | answered / partial / unanswerable 三类的宏平均 F1，附混淆矩阵 |
| 风险–覆盖曲线 | 按置信度阈值变化时，"回答的题占比"与"回答中出错的比例"的关系；报告选定阈值下的工作点 |

全量题按 AmazonQA 银标报告（注明银标及其语料前提），约 200 题按人工金标报告；结论以金标为准。

### 6.2 回答质量

- **是非题准确率：** 与人工结论对比；与社区多数回答的一致率作为弱参考，单独列出。
- **结论支持率：** 把回答拆成原子结论，统计被所引证据直接支持的比例。以人工为准，LLM 评判只做辅助，并报告它与人工的一致率。
- **引用正确率：** 引用的证据确实支持对应结论的比例。
- **越界引用数：** 引用了其他商品的证据，目标为 0。

### 6.3 检索

在有 qrels 的可答题上计算 Recall@K（重排前候选）、Hit@5、MRR@10、nDCG@5。消融顺序：BM25 → 向量 → 混合 → 混合 + BGE → 再加改写重检索。没有支持证据标注的题不进入分母。

### 6.4 系统

P50/P95 端到端延迟、首个进度事件延迟、首个答案块延迟、每题成本、各通道降级率、重试率。另设一项必须为 0 的指标：**服务故障被报告成"评论无法确认"的次数**。

### 6.5 对照基线

| 基线 | 用来说明什么 |
|---|---|
| B0：只给商品名的 LLM，无检索 | 不用证据时会过度回答，体现拒答的价值 |
| B1：把该商品的全部评论塞进上下文，无检索 | 诚实的强基线；检索方案要在大评论池商品、成本或延迟上胜过它，否则如实报告 |
| B2：AmazonQA 自带的可答性分类器 | 在金标上比较本系统的拒答判断 |
| 本系统 | 混合检索 + 重排 + 可答性判断 + 引用 |

### 6.6 报告规则

- 固定数据版本、代码版本、模型版本和 manifest。
- 按品类、题型分别报告；对同一题的方案差值做重采样，给出 95% 置信区间。
- 附失败案例：误拒、该拒没拒、越界引用、冲突证据处理错误。
- **不预设目标数字。** 在 dev 集跑出基线后再定目标；没有实测之前，对外不写任何提升数字。

## 7. 不做什么

| 不做 | 原因 |
|---|---|
| 跨商品对比与推荐（"哪款更好""推荐一款"） | AmazonQA 没有对比类标注，无法评测；识别后提示用户选择单个商品 |
| 回答评论以外的事实：价格、库存、物流、促销、售后政策、官方参数 | 评论不是这些信息的可靠来源；路由为"不在服务范围" |
| 医疗、安全、法律类的确定性结论 | 只转述评论中的个人体验并标注，不给出"可以 / 安全"的判断 |
| 全量 1400 万评论入库 | 先在固定抽样上把链路和评测做完整，再按同一格式扩容 |
| 训练生成模型或向量模型 | 生成用 Claude Haiku 5.5，向量和重排用现成的 BGE 模型；唯一的训练环节是第 6 阶段微调可答性模型 |
| 整体好评率、情感占比等统计 | 检索到的 Top-K 不能代表全部评论；首版只回答具体问题 |
| 把社区回答当作证据 | 社区回答是评测参考，不是评论证据；混用会导致泄漏和不可追溯 |
| 图片、视频评论 | 首版只处理文本 |
| 用户账号、真实电商平台接入、多租户 | 原型阶段不需要 |
| 图模式逐 token 流式 | 首版采用"进度事件 + 校验后分块发布"，并如实描述 |
| 承诺自动校验百分之百正确 | 校验降低错误，但不消除错误；以评测数字说话 |
| 与 Amazon Rufus 等完整购物助手竞争 | 项目价值在"有证据才回答、该拒就拒、每一步可评测"，不在功能覆盖面 |

## 8. 已决定事项

以下事项都已在 [改动方案](roadmap_cn.md) 第 2 节定下，如需调整，改那里。本定位带来的优先级：**F2 商品过滤、F4 可答性、F5 引用、F7 评测**最先做，其余排在后面。

1. **完整评论来源（已解决）。** 用 `val-qar_products.jsonl`，见 5.3 节。
2. **不用 OpenSearch（已决定）。** 目标架构选择 OpenSearch 做全量 BM25。但有了商品硬过滤后，BM25 只需在单件商品的评论上计算（中位数 31 条，P99 约 900 条，最多约 9,000 条），在应用内按商品建索引并缓存就足够，而且仍然是真正的 BM25。首版不引入 OpenSearch，等评论规模或延迟数据证明需要时再加，以减少双存储同步的运维负担。
3. **状态命名（已决定）。** 沿用小样本代码的 `answered / partial / unanswerable`；服务故障单独用 `service_status` 表示。
4. **中文提问的范围（已决定）。** AmazonQA 是英文，正式评测用英文原题；中文提问作为 P2 功能，用单独的小题集评测，不混入主指标。

## 9. 对外一句话

> 面向购前场景的单商品评论问答：选定商品后，基于该商品买家评论作答，每个结论附可回查的评论引用；评论不足以回答时明确拒答。在 AmazonQA 多品类数据上，用人工金标评测可答性判断、引用正确率和检索效果。

最后一句中的评测在完成之前，只能写成"设计并实现评测方案"，不能写成已取得的结果。
