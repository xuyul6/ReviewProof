# ReviewProof 技术报告

日期：2026-10-29。代码版本：`main`，第 5b 阶段完成后（误拒修复实验已回滚，见 6.3 节）。

本文面向第一次看这个项目的读者，说明系统做什么、怎么做、效果如何、还有哪些局限。设计取舍和开发中遇到的问题见[设计决策与问题复盘](design_and_lessons_cn.md)，范围和非目标见[项目定位](product_positioning_cn.md)。文中的评测数字都来自 `reports/eval/<name>/metrics.json`；方括号是 bootstrap 95% 置信区间。

## 摘要

ReviewProof 是一个购前单商品评论问答系统：用户选定一件商品后提问，系统只依据这件商品的买家评论作答，每条结论附评论引用，并判断评论能否回答这个问题（能回答 / 部分能回答 / 无法确认）。数据是 AmazonQA 验证集里抽样的 100 件商品。检索按评论量自适应：评论少的商品把全部评论交给模型，评论多的商品用向量和 BM25 两路召回、RRF 融合、交叉编码器重排。问答由 LangGraph 工作流完成，生成用 Claude Haiku 5.5，引用由代码核验。

评测先用 AmazonQA 自带的银标试跑，发现它的检索参考证据就是 AmazonQA 自己的 BM25 结果，不能用来比较检索方案；于是做了 200 题金标（Claude 子 agent 预标、一位人工逐题审核）。金标下：混合检索加重排的 nDCG@5 比 BM25 高 0.211 [0.135, 0.286]（dev）和 0.238 [0.148, 0.318]（test）；完整工作流答或拒的准确率为 0.850 [0.780, 0.910]（dev）和 0.830 [0.750, 0.900]（test），主要错误是误拒。一次针对误拒的提示词修复在 dev 上没有净收益，已回滚。

## 1. 问题与定位

购物时常有评论才能回答的问题："这个尺寸适合 2015 款车吗""声音大不大"。通用大模型只拿到商品名时会凭常识作答；而评论确实没提到时，正确的回答是"评论无法确认"。所以这个项目的核心指标是**可答性**：

- **answered**：评论直接回答了问题的每个部分；
- **partial**：只回答了一部分，或只有相近情形（例如别的年款）；
- **unanswerable**：评论里没有相关内容。

服务出错（检索或模型调用失败）单独表示为 `service_status=failed`，不能说成"评论无法确认"。这条规则从检索层一直贯穿到接口、前端和评测分母。

不做的事：跨商品推荐、价格和库存、多轮对话、生成商品摘要（见定位文档）。

## 2. 数据

### 2.1 来源和抽样

AmazonQA（Gupta et al., 2019）提供 `val-qar_products.jsonl`（商品的完整评论）和 `val-qar.jsonl`（问题、社区回答、AmazonQA 检索出的评论片段和可答性标签）。两份文件从 AmazonQA 官方 S3 下载，导入前按清单核对 SHA-256；本仓库不分发数据。

清单 `samples/manifest_v1.json` 从 4 个品类（Electronics、Home_and_Kitchen、Automotive、Beauty）按评论量分 3 档（≥200、50–199、<50）抽样 100 件商品，按商品分为 dev（30%）和 test，种子 20261027。合计 22,433 条评论、24,599 个评论块、767 道题。

### 2.2 两个关于数据的发现

1. **问题文件里的"评论"是片段。** `val-qar.jsonl` 里每道题附带的约 10 条评论，是 AmazonQA 用 BM25 从完整评论中检索出的片段。所以检索语料改用 `val-qar_products.jsonl` 的完整评论，片段只用于构造银标参考证据。
2. **可答性标签是分类器给的。** `is_answerable` 来自 AmazonQA 训练的分类器，不是人工标注，所以只能算银标。金标和银标的二值一致率是 0.78，kappa 只有 0.397（dev）和 0.360（test）。

### 2.3 切分和存储

不超过 1,200 字符的评论整条作为一个块（评论长度中位数 238 字符）；更长的按句子打包到约 800 字符，相邻块重叠一句。每个块保存它在原评论中的偏移，`块文本 == 评论文本[start:end]`，前端可以在原评论里高亮引用。评论 ID 是系统生成的（`{asin}-r{序号}`），不是 Amazon 的评论 ID。

数据存进 PostgreSQL 16 + pgvector，向量是 BGE-M3 的 1024 维稠密向量。问题、社区回答、片段和标签只存在 `questions` 表，有测试保证它们不会进入评论表、块表或任何提示词。

## 3. 系统

### 3.1 总览

```
问题 → 规划（范围判断、是否是非题、英文检索词）
     → 检索：评论 ≤ 6,000 token 的商品（100 件里 28 件）把全部块作为证据
             其余商品：BGE-M3 稠密 ∥ BM25 各取 50 → RRF(k=60) → 前 40 → bge-reranker-v2-m3 → 8 条
     → 证据评估（三态、支持块、缺口、改写检索词）
     → 证据不足时改写重检索（最多 1 次，只对混合检索的商品）
     → 带引用生成（结构化输出）→ 代码核验引用 → 固定文案渲染
     → SSE 推送进度和答案；每次运行写入 qa_runs 表
```

### 3.2 检索

- **自适应策略：** 一半商品的评论不到约 3,000 token，对这些商品做检索没有意义，全部交给模型更可靠。
- **两路召回：** 向量检索在单件商品内精确排序（最多约 9,000 条评论，不需要 ANN 索引）；BM25 按商品在内存里建索引并缓存。中文问题由规划节点翻成英文检索词。
- **融合和重排：** RRF 只看名次，不受两路分数量纲不同的影响；重排模型对融合后的前 40 条打分，取前 8 条。
- **故障处理：** 每一路记录状态、原因、耗时和命中数。有召回通道失败、并且融合后为空时，结果标为 `failed`，而不是"没有证据"。

### 3.3 问答工作流

LangGraph 是唯一的编排路径，降级在节点内部处理：

- **规划**判断问题是否在评论能回答的范围内（价格、库存、物流、问卖家、推荐别的商品等直接判出范围），是否是是非题，并写出英文检索词。规划失败时用启发式规则继续，标为降级。
- **证据评估**是可答性的唯一裁决者：判三态，列出支持的块和缺口；后面的步骤只能把状态降低，不能升高。
- **生成**只在 answered 或 partial 时运行。每条结论必须引用块 ID；是非题先写下它回答的是哪一问（`verdict_question`），最后写结论（是 / 否 / 意见不一 / 无法确认）。
- **核验**是纯代码：删掉不在本次候选里或属于其他商品的引用，删掉没有引用的结论；没有结论剩下，或是非结论是"无法确认"时，降为 unanswerable。
- **渲染**用中英两套固定文案，回答语言由代码根据问题判断。

模型调用都用 Anthropic SDK 的结构化输出（Pydantic schema）；任何调用失败或输出不合 schema 都按服务故障处理。

### 3.4 接口、前端和部署

FastAPI 提供商品列表、示例问题、评论原文、运行记录和流式问答（SSE：`run_started`、每个节点一条 `progress`、`answer_chunk`、`citations`、`done`）。答案在引用核验后分段发送，不是逐 token 生成。Vue 3 前端展示进度、三态徽标、引用和原评论高亮。只读 MCP 服务提供商品列表、检索和取评论三个工具。

`docker compose up --build` 启动全栈：数据库、导入任务（下载、核对、切分、向量化，可重复运行）、接口和网页。

## 4. 评测方法

### 4.1 为什么不能用银标比较检索方案

银标的参考证据是题目自带的约 10 个片段，也就是 AmazonQA 自己的 BM25 前 10 条。用它评检索，衡量的是"和 AmazonQA 的 BM25 有多像"：BM25 天然占优，重排找到 BM25 没找到的相关评论反而会被扣分；而且每题约 10 个参考块，Recall@5 的上限只有约 0.5。银标试跑（[pilot-dev](../reports/eval/pilot-dev/report.md)、[pilot-test](../reports/eval/pilot-test/report.md)）因此只作记录，不下结论。

### 4.2 金标

- **抽样：** dev 和 test 各 100 题，按品类 × 题型 × 银标分层；每个 split 20% 的题盲标。
- **候选池：** 全量上下文商品取全部块；其他商品取四种检索方案（BM25、向量、混合、混合 + 重排）各自前 10 的并集，按块编号排序展示，不暴露哪个方案排得靠前。
- **标注：** 按[标注规范](annotation_guidelines_cn.md)（gold-v1）标三态、是非结论和每个块的证据等级（2 = 单独就能支持答案，1 = 相关但不够，0 = 无关）。Claude 子 agent 只看题目和候选块（看不到银标、片段和社区回答）预标，再由一位人工逐题审核；盲标题先由人独立标完，才能看到预标。
- **结果：** 200 题里人工改了 8 题。最终 answered 109、partial 48、unanswerable 43；2 级证据块 881 个。盲标题上人和预标的可答性一致 15/20（dev，kappa 0.593）和 19/20（test，kappa 0.919）。

### 4.3 指标和对照

- **检索：** hit@k、Recall@k、MRR、nDCG@5（相关 = 2 级证据；分级 nDCG 用 0/1/2 作增益）。只在混合检索商品、金标可答的题上计算（dev 56 题、test 62 题）。
- **可答性：** 二值准确率（答或拒是否正确，partial 算答）、误拒率、正确拒答率、三态完全一致率、是非题结论准确率。
- **对照系统：** B0 不给证据，只给问题；B1 把全部评论放进上下文（只在混合检索商品的 70 题上跑，和工作流在同一批题上比）；B2 是 AmazonQA 自带的分类器，即把银标当预测。
- **统计：** 每个指标做 1,000 次 bootstrap 重采样（种子 20261027）；方案比较用配对差值的区间。服务故障不进任何可答性分母，单独计数。两次正式金标评测都没有服务故障，也没有越界引用。

## 5. 结果

### 5.1 检索（nDCG@5）

| 方案 | dev（56 题） | test（62 题） |
|---|---|---|
| BM25 | 0.431 [0.337, 0.526] | 0.411 [0.336, 0.493] |
| 向量 | 0.477 [0.394, 0.567] | 0.513 [0.425, 0.601] |
| 混合（RRF） | 0.505 [0.405, 0.601] | 0.518 [0.436, 0.610] |
| 混合 + 重排 | 0.642 [0.555, 0.729] | 0.650 [0.565, 0.733] |
| 配对差值：混合 + 重排 − BM25 | 0.211 [0.135, 0.286] | 0.238 [0.148, 0.318] |
| 配对差值：混合 + 重排 − 混合 | 0.138 [0.068, 0.212] | 0.132 [0.074, 0.192] |

混合 + 重排在两个 split 上都最好，比 BM25 和不重排的混合都高，差值区间不跨 0。银标试跑的结论（BM25 的 hit@5 最高）在金标下反过来了，印证了 4.1 节的判断。

### 5.2 可答性

| | dev（100 题） | test（100 题） |
|---|---|---|
| 准确率：完整工作流 | 0.850 [0.780, 0.910] | 0.830 [0.750, 0.900] |
| 准确率：B0 不给证据 | 0.300 [0.210, 0.400] | 0.250 [0.170, 0.340] |
| 准确率：B2 AmazonQA 分类器 | 0.780 [0.700, 0.860] | 0.780 [0.700, 0.860] |
| 误拒率：工作流 / B2 | 0.143 / 0.156 | 0.175 / 0.163 |
| 正确拒答率：工作流 / B2 | 0.826 / 0.565 | 0.850 / 0.550 |
| 三态完全一致：工作流 | 0.710 [0.620, 0.790] | 0.720 [0.630, 0.810] |
| 是非题结论准确率：工作流 | 0.583（12 题） | 0.533（15 题） |

- B0 不给证据时几乎全部拒答（误拒率 0.883 和 0.912），准确率接近金标不可答题所占的比例。它说明工作流的回答来自检索到的证据；而"不给证据时模型会凭常识编答案"这个担心在这里基本没有出现：金标不可答的题，B0 在两个 split 上都只答了 2 道。
- 工作流的点估计高于 B2，主要差在正确拒答率；但准确率区间重叠，没做配对检验，不能说显著更好。

### 5.3 和全量上下文（B1）对比

同一批 70 题（混合检索商品）：

| | dev | test |
|---|---|---|
| 准确率：工作流 / B1 | 0.843 / 0.929 | 0.814 / 0.743 |
| 三态完全一致：工作流 / B1 | 0.714 / 0.714 | 0.714 / 0.614 |
| 每题成本：工作流 / B1 | $0.00105 / $0.0285 | $0.00110 / $0.0110 |
| 延迟 P50：工作流 / B1 | 17.9 / 7.1 秒 | 17.3 / 7.7 秒 |

两个 split 的方向相反、区间重叠，这个样本量下分不出准确率高下。B1 每题贵 10–27 倍，但延迟更低（一次长上下文调用，没有重排和多轮调用）。按评论量分档，B1 也没有在哪一档稳定领先，所以没有调整 6,000 token 的全量上下文阈值。

### 5.4 成本和延迟

完整工作流平均每题 3.14 次 Claude 调用，每题约 $0.0011；延迟 P50 14.5 秒、P95 27.1 秒（dev，CPU 上运行重排）。两次金标评测（含 B0、B1）合计花费 $3.01。

## 6. 错误分析

### 6.1 误拒

25 道误拒（dev 11、test 14；金标 partial 17、answered 8）按原因分三类：

1. 11 道：评估判能答或部分能答，生成给了"无法确认"的是非结论，核验规则把整题降为不可答；
2. 11 道：评估直接判不可答，多数只有相近情形的证据，规范算 partial；
3. 3 道：规划判成超出范围。

25 道里有 22 道是预标子 agent 在审核备注里列为边界情况的题（全部可答题里这个比例是 52%）：误拒集中在 partial 和不可答的边界上，金标本身在这些题上也有判断空间。

### 6.2 是非题结论

是非题结论准确率只有 0.583 和 0.533，题数只有 12 和 15，区间很宽（dev [0.333, 0.833]）。两个 split 共 12 道错题，最多的两类：金标是"是"（多为只有相近情形的 partial 题），系统却给了"无法确认"并因此拒答，6 道，和 6.1 节的第 1 类误拒重合；评论意见不一，系统却给了"是"，4 道。

### 6.3 一次没有成立的修复

针对 6.1 节，改了三处（"无法确认"只降为 partial；评估提示词按规范改写三态定义；"选哪个尺码"不算推荐别的商品），只在 dev 上验证：

| dev | 修复前 | 三处都改 | 回滚第一处 |
|---|---|---|---|
| 准确率 | 0.850 [0.780, 0.910] | 0.850 [0.770, 0.920] | 0.850 [0.770, 0.920] |
| 误拒 / 误答（题数） | 11 / 4 | 4 / 11 | 8 / 7 |

修改只是在误拒和误答之间转移错误：造成误拒的规则同时也在挡误答；模型还把"相近情形"推广到了别的设备型号。同样的提示词跑两次，就有 3 题结论不同，和修复的效应一样大。三处修改全部回滚，test 没有复跑，第 5 节的数字对应的仍是回滚后的代码（和修复前相同）。详见复盘文档 9.5 节。

## 7. 局限和有效性威胁

- **金标不是双人独立标注：** 子 agent 预标、一位人工审核；审核只改了 8/200 题，6 道盲标分歧终审都采用了预标，可能有锚定效应。盲标一致率是人和子 agent 之间的。
- **同源偏差：** 预标子 agent 和被测系统都是 Claude 模型，同类错误未必能被审核发现。
- **候选池有限：** 证据等级只覆盖四种方案前 10 的并集（加标注时搜到的块）。Recall 的分母只含池内的相关块，可能偏高；预标为无关、审核时折叠的块不一定逐块复核过。
- **dev 和 test 的使用：** dev 用于调试工作流，数字可能偏乐观；test 上有一道试跑错题（21567，不在金标里）参与过提示词修改；误拒分析看过 test 的错例，但修复没有在 test 上测量。
- **样本量：** 每个 split 100 题，准确率区间宽约 ±0.07；是非题只有十几道。
- **单次运行：** 每个系统每题只跑一次，LLM 输出有随机性（6.3 节）。
- **数据范围：** 只有 4 个品类、100 件商品、英文评论；中文提问没有单独评测。

## 8. 复现

- **一键启动：** `docker compose up --build`（见 README），在干净克隆、没有 `.env` 的环境里验证过。首次运行要下载约 1.5 GB 数据和两个模型，并在 CPU 上计算 24,599 个块的向量：Apple 芯片的 Mac 上 Docker 里实测每分钟 85–96 块（4 个多小时），本机 Python 约 40 分钟，所以 README 给了先在本机导入的做法。
- **评测：** `python -m reviewproof.eval --split dev --name gold-dev --labels annotations/gold_v1/labels.jsonl`，会调用 Claude；`--retrieval-only` 只做检索评测，不调用 Claude。每份报告的 `config.json` 记录代码版本、数据 SHA-256、模型和参数。
- **测试：** Python `unittest`（数据库测试只连名字以 `_test` 结尾的库）和前端 Vitest，GitHub Actions 上运行。

## 9. 后续工作

- **可答性模型（第 6 阶段）：** 用 AmazonQA 训练集的银标微调交叉编码器，在金标 dev 上画出误拒和误答随阈值变化的曲线、选定工作点，再在金标 test 上和 LLM 评估、AmazonQA 分类器比较一次。这是 6.3 节那种取舍的正确做法。
- **评测的分辨力：** 同一版本多次运行、对翻转的题做配对检验，或扩大金标题量。
- **结论支持率：** 现在只核验引用 ID，没有逐条核对结论是否被引用的评论支持。
- **中文提问小题集、全量上下文阈值的专门调参。**
